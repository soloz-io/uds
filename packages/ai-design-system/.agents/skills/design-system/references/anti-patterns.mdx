## Anti-Patterns to Avoid

This document outlines common mistakes that reduce reuse and introduce feature coupling in ai-design-system.

---

### 1. Feature-Aligned Names in Reusable Layers

**Anti-Pattern**: Naming composites and blocks with feature-specific terminology.

**Incorrect**:
```tsx
// ❌ Composite name tied to a specific feature context
export function WorkflowObservabilityRunInboxList() {
	// ...
}

// ❌ Block name tied to a specific feature context
export function WorkflowObservabilityInboxPanel() {
	// ...
}
```

**Correct**:
```tsx
// ✅ Composite name is generic and reusable
export function InboxList() {
	// ...
}

// ✅ Block name is generic and reusable
export function InboxPanel() {
	// ...
}

// ✅ Feature name can be feature-aligned
export function WorkflowRunInboxFeature() {
	// ...
}
```

**Why**:
- Preserves reuse across multiple features.
- Prevents business-context leakage into reusable layers.
- Reduces refactor churn when use cases expand.

**Rule**:
Composites and blocks must use general names that any feature can consume. Only features may use feature-aligned names.

---

### 2. Exporting Non-Feature Components from Root

**Anti-Pattern**: Exporting composite/block/primitives component values from package root.

**Incorrect**:
```ts
// ❌ Root value exports leaking lower layers
export { AppHeader } from './composites/AppHeader'
export { SectionLayout } from './blocks/SectionLayout'
```

**Correct**:
```ts
// ✅ Root value exports are feature-only
export * from './features'

// ✅ Lower layers can remain type-only at root
export type * from './composites'
export type * from './blocks'
```

**Why**:
- Prevents consumers from bypassing feature governance.
- Keeps app-level composition centered in feature APIs (for example, `PageLayout` for header usage).
- Reduces coupling to internal layers and enables safer DS evolution.

**Rule**:
Package root must expose runtime component values from `features` only. Consumers must not depend on root-level `AppHeader`/`SectionLayout` values.

---

### 3. Defining Action Handlers Inside Stories

**Anti-Pattern**: Creating local `handle*` functions or inline `on...={() => ...}` callbacks in feature stories.

**Incorrect**:
```tsx
export const WithStateManagement: Story = {
	render: () => {
		const hook = useMyFeatureMock()

		const handleTabChange = (value: string) => {
			hook.onTabChange(value)
		}

		return <MyFeature onTabChange={handleTabChange} onSave={() => console.log('saved')} />
	},
}
```

**Correct**:
```tsx
export const WithStateManagement: Story = {
	render: () => {
		const hook = useMyFeatureMock()

		return <MyFeature onTabChange={hook.onTabChange} onSave={hook.onSave} isLoading={hook.isLoading} />
	},
}
```

**Why**:
- Stories must reflect the real hook contract used by consumers.
- Story-local handlers hide missing hook state and create test-only behavior.
- Validation can only guarantee consistency when handlers come from hooks, not ad hoc story code.

**Rule**:
All action handlers used by `WithStateManagement` stories must come from mock hooks. Stories must not define local `handle*` functions or inline callback props.
